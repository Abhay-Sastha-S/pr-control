"Open" is not a status. Which one do I merge first?

One page for every pull request you have in flight — joining GitHub, the review channel that asked for review, the tickets they close, and the local Claude Code sessions that wrote them. Then it works out the order they actually have to land in.

Illustrative — the real tree is built from your own PRs

Why it exists

"Open" collapses four different situations into one word.

Waiting for a first review, waiting on requested changes, approved and waiting for a human to press merge, and blocked behind someone else's deploy are completely different problems — and only one of them is your move. GitHub shows all four as a green "Open".

The merge order lives where no API can see it.

A sentence in a Slack thread — "merge the backend one first or the page 404s" — two PRs closing the same ticket, a pair of stacked branches. Get the order wrong and you spend the afternoon rebasing.

A PR nobody was told about isn't in review.

It's just open. That gap is invisible on GitHub, where the PR looks perfectly healthy.

The reasoning is in a session you can't name.

Why you made a call four days ago is in a Claude Code transcript identified by a UUID. Each PR here links to the sessions that touched it, with a ready-to-paste claude --resume.

Every one of those answers already exists. They're just in four tools that don't join to each other. This does the join.

What it computes that nothing else does

The heart of it is the edge set — a must merge before b — derived in precedence order:

SourceMeaning
Channel-stated chainsSomeone said so in the review channel. Highest authority, and hand-maintained in config because no API exposes it.
Branch stacksb's base branch is a's head. Structural, so it's inferred.
Shared open ticketsTwo open PRs closing the same ticket ship together.
Same-repo orderingOlder open PRs in a repo where you have one merge first, or you rebase.

Ties break on a configurable service rank — shared libraries before services, services before user-facing apps. Other people's PRs are pulled in only when they share an edge with one of yours, so the page stays about your work while still showing who you're waiting on.

Nothing about your organisation is in the repo

Every organisation-specific value — your org, your GitHub login, your Slack workspace and channel, your teammates, your Linear workspace, your dependency chains — lives in one config file that is never committed. The release check fails the build if a config file, a Slack export, or a built page is ever staged, so the repo can't start leaking by accident.

cp config.example.json ~/.claude/pr-control/config.json
$EDITOR ~/.claude/pr-control/config.json

The page template holds no organisation strings either — it labels itself at runtime from a meta block the build injects.

What it reads

Worth knowing before you run it, because the answer is "quite a lot":

  • GitHub, through the gh CLI you're already signed in to — PR metadata only, for the repos you list.
  • Slack, read-only, through an MCP server — one channel, searched for review requests. The page never gets Slack write tools; replying is copy-to-clipboard plus a deep link into the thread.
  • Linear, read-only — issue titles and statuses.
  • ~/.claude/projects, read-only — your local Claude Code transcripts, scanned for PR URLs. Transcript content never leaves your machine; only the session id, project directory, and existing summary line are used.

Everything runs locally. The only thing that goes anywhere is the finished page, and only when you publish it.

The pipeline

gh pr list ─────────────► prs.jsonl ──┐
slack search ──► slack_mentions.json ─┤
linear issues ─► linear_issues.json ──┼──► merge.py ──► prdata.json
extract_sessions.py ──► sessions.json ┤                      │
gh pr list (bodies) ──► tickets.jsonl ┘                      ▼
                                              build_page.py ──► pr-control.html
                                                                     │
                                            scripts/smoke-page.mjs ──┴──► publish

That last step earns its place. The page is one large inline script, and a syntax check only proves it parses — a const used before its declaration parses perfectly and then renders a blank page. The smoke test executes the built page against a DOM shim and fails on load-time errors. It caught exactly that bug while this was being packaged.
